# v0.4b Hono 延迟核查（相对 v0.4a）

依据 [codex-contract-v0.5a.md](codex-contract-v0.5a.md) §0。比较 v0.4a `97f0e9d` 与 v0.4b `ad11701` 的 `npm run bench:latency:hr`（Hono 适配器，100 并发，Δp99 门槛 1000 µs）。**结论：测量噪声，不是 v0.4b 回退。未改代码，未改门槛。**

## 方法

- 同一台机器：Node v24.22.1；linux 6.12.113+ x64；8 logical CPUs（`Intel(R) Xeon(R) Processor`）；16 GiB RAM。
- 用 `git worktree` 分别检出两个提交，工作区 `/workspace/agent-guard`（当时 `e2ce011`）未改动。两个 worktree 各自安装与该提交一致的 `node_modules`。
- 交替各跑 3 次完整 `bench:latency:hr`（顺序：v0.4a、v0.4b、v0.4a、v0.4b、v0.4a、v0.4b）。每次默认 `HR_RUNS=3`、`HR_CONNECTIONS=100`、`HR_LOW_CONNECTIONS=10`、warmup 1 s、duration 3 s；Δ = on 中位数 − off 中位数（微秒，nearest-rank）。跑次之间 settle 5 s。
- 开始：2026-11-11 22:35:46（HKT / UTC+8）；结束：2026-11-11 22:51:33（HKT）。每次 wall ≈ 152–153 s。
- 无请求错误。50k 客户端堆增量全部通过（v0.4a 约 8.56–8.57 MiB，v0.4b 约 8.60 MiB，门槛 10 MiB）。
- **负载说明（如实）：** 机器不是空闲的。全程有常驻进程占用 CPU（`sand-host` node 约 27%，一组 Chrome 渲染进程合计约 17–20%）。各次开始时 1 分钟 load average 在 1.83–3.28。两个版本在同一环境下交替测量，负载条件对双方是对称的，但不能当成专用空闲机上的实验室数字。原始 JSON 留在执行环境的 `/workspace/ag-runs/v0.5a-hono/`（不入库）。

门槛（未改）：Δp50 ≤ 200 µs，Δp99 ≤ 1000 µs。判定按单次完整 `bench:latency:hr` 的中位数，不是跨 3 次外层运行再取中位数。

汇总（3 次外层运行）：

| 版本 | Δp50 中位数（范围） | Δp99 中位数（范围） | off p99 中位数（范围） | 通过次数 |
| --- | --- | --- | --- | --- |
| v0.4a | −46（−48…18） | **−194（−703…1074）** | 6658（6127…7719） | 2 / 3 |
| v0.4b | −23（−165…0） | **225（−28…1431）** | 6298（5620…6934） | 2 / 3 |

- 两个版本的 Hono Δp99 分布重叠。v0.4b 中位数比 v0.4a 高 419 µs，远小于各自的运行间波动（v0.4a 极差 1777 µs，v0.4b 极差 1459 µs）。
- 两边都是 3 次里有 1 次略过 1000 µs 门槛（v0.4a 跑次 2 为 1074，v0.4b 跑次 2 为 1431）。不能从「有一次超标」推断回归。
- Δp50 两边都稳定低于 200 µs。
- 对照基线本身也在动：Hono off p99 绝对值约 5.6–7.7 ms，单版本内波动已超过 1 ms 门槛。门槛量级和基线噪声相当，单次判定会抖。
- 10 并发 Hono Δp99 全部远低于门槛（v0.4a：137 / 190 / −16；v0.4b：31 / 253 / 258）。

`guard.inspect` 微基准（人机首页，ns/op 中位数）：v0.4a 为 2411.5 / 2423.5 / 2424.0；v0.4b 为 2624.8 / 2475.3 / 2366.2。两边重叠，看不出稳定的热路径回退。

## 同一次运行里其他适配器（100 并发 Δp99）

噪声不是 Hono 独有。Express 与 node 适配器同样会在个别跑次超过 1000 µs，且两个版本都会出现。

| 适配器 | v0.4a Δp99（中位数，范围） | v0.4b Δp99（中位数，范围） | 超标次数（a / b） |
| --- | --- | --- | --- |
| express | 902（116…986） | 568（462…1295） | 0 / 1 |
| node | 345（−359…1067） | −414（−572…1087） | 1 / 1 |
| hono | −194（−703…1074） | 225（−28…1431） | 1 / 1 |

第三次外层运行两个版本都是全绿；第一、二次各有不同适配器失败。没有「v0.4b 全面变慢」的形态。

## 与此前验收数字的关系

同一机器上更早的验收（不是本次交替协议，只作对照）也已经表现出抖动：

- v0.4a 验收：Hono 100 并发 Δp99 一次 1519 µs（未过）、一次 −1425 µs（通过）。
- v0.4b 验收三次：Hono Δp99 为 1069 / 1119 / 1115 µs（中位数 1115，三次都略过门槛）。本次交替重测里 v0.4b 中位数是 225 µs，且有一次通过很多、一次未过，说明前一次「三次都略超」并不能单独证明回归——同样的门槛在 v0.4a 上也会偶尔失败，且基线 p99 本身在毫秒级波动。

## 结论与建议

**结论是测量噪声。** 不定位 CryptoProvider 拆分或适配器路径，不改代码，不改门槛。

建议（需 Dan 批准后才改门槛判定，本次只记录）：把 `bench:latency:hr` 的门槛判定改为「多次完整运行的 Δp99 中位数对照门槛，并在报告里写波动范围」；单次略超不再单独判失败。1000 µs 的绝对门槛可以先保留，但不要用单次结果当作回归证据。若以后要收紧或放宽门槛本身，需要单独批准。
